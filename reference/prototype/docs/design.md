# Seam: робочі вимоги та перший прототип

Документ фіксує обговорення переписування Seam. Назви класів, структура модулів і конкретні сигнатури API ще не визначені. Поточна реалізація є джерелом досвіду, а не основою, яку потрібно зберегти.

## Призначення

Seam є Java-бібліотечним модом для запуску незалежних світів у звичайній Mindustry. Окремий світ має власний runtime, включно з тайлами, будівлями, юнітами, кулями, станом команд, правилами, хвилями, логікою та погодою.

Підтримка Android і headless потрібна від початку. Кастомний клієнт або launcher неприпустимий. Цільові масштаби включають повнорозмірні карти та дуже малі підсвіти.

Версія гри зафіксована та змінюється виключно вручну. Початкова ціль переписування, визначена під час обговорення, є v160.7. Поточний проєкт усе ще використовує v159.7.

## Межа відповідальності

Seam забезпечує ізоляцію, керування runtime та API для довільної роботи зі світами і їхніми об'єктами. API має дозволяти залежним модам реалізовувати перенесення, злиття, розділення та взаємодію світів.

Просторові перетворення, рух світів, фізика кораблів, вибір областей карти й правила зв'язків визначає залежний мод. Готові ігрові механіки та універсальна операція злиття світів до ядра не входять.

Визначення контенту спільні. Seam не надає світозалежної підміни Block, UnitType або інших визначень контенту.

Повна прозора сумісність зі сторонніми модами є ціллю користувача. Її фактичні межі ще потрібно встановити. Підміна глобальних полів гри сама собою не ізолює власний глобальний стан довільного стороннього мода.

## Ядро та стандартні компоненти

Ядро надає механізми ізоляції, контекст виконання, належність об'єктів та керування життєвим циклом. Конкретне розмежування цих механізмів потребує прототипу.

Стандартні компоненти є необов'язковими загальними реалізаціями, які залежний мод може використовувати, налаштовувати або замінювати через те саме API. Вони охоплюють оновлення, базове відображення, звук, збереження, синхронізацію та прив'язки життєвого циклу.

Світ може відображатися одночасно з іншими, відкриватися окремо або взагалі не відображатися. Рендер і звук не повинні бути умовою існування runtime.

API має дозволяти керувати системами окремо. Політику оптимізації залежного мода Seam не нав'язує.

Спільні предмети ванільних ядер, оплата будівництва на різних рівнях карти та спільний unit cap є сценаріями перевірки достатності API. Конкретні режими спільної економіки й обліку зараз не специфікуються як окремий продукт Seam.

## Належність та життєвий цикл

- Зміна світу для Unit або Building має зберігати Java-екземпляр у межах кожного процесу.
- Перенесення не має вимагати знищення об'єкта та створення його копії.
- Світ може належати карті, UI, будівлі, юніту, іншому світу або об'єкту залежного мода.
- Зміна світу власника не є знищенням власника або прив'язаного підсвіту.
- Карта та UI є базовими сценаріями стандартних прив'язок; потрібні також інші загальні прив'язки.
- Світ, що є частиною карти, зберігається разом із нею. Окреме сховище не є стандартною поведінкою.
- Тимчасовий світ демонстрації існує до закриття її UI та не потребує збереження.
- Клієнтські світи без серверного аналога мають підтримуватися, зокрема для демонстрацій.

Потрібно окремо уточнити семантику живого runtime після вивантаження батьківської карти. Збереження даних і продовження симуляції після виходу є різними можливостями.

## Технічні факти з читання коду

Ці спостереження не є результатами runtime-тестування.

- Поточний Seam послідовно викликає SubWorld.update() з Trigger.update. Основна симуляція різних світів не запускається паралельно.
- SubWorldContext підміняє глобальні поля Mindustry/Arc, групи сутностей і частину часу. Поточний список підмін не слід вважати повним.
- SubWorldEvents тимчасово замінює глобальний набір слухачів локальним. Зареєстровані зовні обробники сторонніх модів тому не отримують подій підсвіту через цей набір.
- У v160.7 Logic.update() звертається до мережевих служб, глобальної логіки та інших служб процесу. Створення окремого Logic не доводить незалежність runtime.
- У v160.7 Logic.updateEntities() також оновлює Groups.effect. Групи, приховані черги та pooling потрібно перевіряти за фактичною версією гри.
- У v160.7 AsyncCore використовує Vars.unitPhysics, якого немає у поточному переліку підмін Seam. Фонові задачі потребують окремого аудиту.
- UnitComp.add()/remove() змінюють облік команди, взаємодіють із фізикою та контролером. Просту пару remove/add не можна вважати доведеним механізмом перенесення.
- Спільні предмети ванільних ядер пов'язані з перерахунком сусідства, місткістю та видаленням ядер. Одноразове присвоєння спільного ItemModule не доводить коректність спільної економіки між світами.

## Перший прототип

Пропозиція реалізації: основну симуляцію спочатку виконувати послідовно в головному потоці. Це не означає відмову від фонових задач; кожна така задача потребує перевірки доступу до світового та глобального стану.

Мета прототипу: основний світ і два підсвіти можуть оновлюватися незалежно без власних ігрових механік та без обов'язкового рендеру.

Перші перевірки:

1. У двох підсвітах різних розмірів сутності, правила, стан команд, час і відкладені дії залишаються у своїх світах.
2. Вкладені виклики A -> B -> A правильно відновлюють попередній контекст, включно з виходом через виняток.
3. Події обробляються у правильному контексті. Завантаження або очищення підсвіту не запускає помилково життєвий цикл основної карти.
4. Фонові задачі не читають стан іншого світу під час перемикання або знищення runtime.
5. Юніт переходить між runtime зі збереженням екземпляра. Перевіряються облік команд, групи, індекси, фізика та контролер. Для Building потрібна окрема аналогічна перевірка.
6. Знищення одного світу звільняє його ресурси й не порушує роботу інших світів.
7. Невеликий сторонній тестовий мод без знання про Seam перевіряє події, власні колекції сутностей та відкладені дії.

Окремий клієнтський сценарій регресії: після фактичного видалення підсвіту не залишаються його циклічні ambient-звуки, а звуки інших світів продовжують працювати. Симптом описаний користувачем зі спогаду про попередній тест; його ще не відтворено, причина не встановлена.

## Анотації та кодогенерація

Відкрите технічне рішення. Власний процесор анотацій не потрібен лише через те, що Seam є бібліотекою.

Можливе застосування внутрішньої генерації: повторюваний код захоплення та відновлення контексту, реєстрація явно описаних систем. Генератор не визначає автоматично, який стан потрібно ізолювати, та не усуває побічних ефектів ванільних методів.

Базове API має бути доступним модам без обов'язкового процесора анотацій. Необхідність генерації слід оцінити після ручного прототипу.

## Інструменти та порядок роботи

Початкова рекомендація, а не вже виконана міграція:

1. Взяти офіційний мінімальний Java-шаблон і вручну зафіксувати цільову версію гри.
2. Використати MindustryClient для локального запуску, якщо перевірка його інтеграції підтвердить придатність.
3. Додати CI та перевірити desktop, Android і headless. Відсутність ручного Android-тесту не підміняти успішним dex-збиранням.
4. Реалізувати й перевірити прототип ізоляції до фіксації публічних сигнатур API.
5. Після прототипу визначити API та межі стандартних компонентів, збереження і мережевого протоколу.

EntityAnno, EnvAlloc та AssetProc не мають встановленої потреби для першого прототипу. Підключення можливе після появи конкретної задачі.

Поточні незакомічені Java-зміни користувача зберігаються. Цей документ не означає дозволу видаляти їх або переписувати історію Git.
